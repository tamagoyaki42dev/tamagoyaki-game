### バグ修正2件

**1. lambda 値型キャプチャバグ（ハーネスバグ）**

`var won := false` が lambda 内部にコピーキャプチャされ、`battle_ended` の `player_won=true` が外側に伝わらなかった。GDScript 4 の仕様：プリミティブ（bool/int/float）は値コピー、Dictionary/Array/Object は参照キャプチャ。

```gdscript
# 修正前（全シナリオ 勝率0% になっていた原因）
var won := false
bm.battle_ended.connect(func(player_won: bool, _loot: Array) -> void:
    won = player_won)  # lambda のローカルコピーを書き換えるだけ
return {"won": won, "turns": turns}  # 常に false

# 修正後
var result := {"won": false}
bm.battle_ended.connect(func(player_won: bool, _loot: Array) -> void:
    result["won"] = player_won)  # Dictionary は参照なので外側に届く
return {"won": result["won"], "turns": turns}
```

**2. ADAPTIVE_B3 戦略の条件反転バグ（ハーネスバグ）**

`do_rotate = (bm.turn_number % 4 == 1)` が「チャージ後の大ダメ（cycle_pos=1）のターンに ROTATE」という逆ロジックになっていた。弱列（CLERIC HP=18）が ATK=32 を食らって即死。

修正：`do_rotate = not (bm.turn_number % 4 == 1)` → 大ダメターン前に STAY で強列を維持。

**GDScript 4 lambda の値型コピーで Claude が無言全敗させた事件**
全7シナリオ death×100 という結果に「ATK=8 の敵に2ターンで全滅は物理的に不可能＝ハーネスバグ」と冷静に気づき調査開始。verbose ログに `BATTLE_ENDED player_won=true turns=2` の直後に `trial0: won=false turns=2` が並ぶのを見て確定。原因は `var won := false` を lambda に閉じ込めたことで、GDScript が「bool は値だからコピー渡し」と判断したため。Claude がコードを書いてその Python 的な感覚でハマり、全シナリオを「敵に一蹴されたチーム」に仕立てた。ユーザーが「物理的に不可能」という診断を先に提供してくれたおかげで即解決。

**「ロジックだけなら余裕」が一番出てくる、の逆説**
ユーザー曰く「いやあロジックだけなら余裕よと思ってたけど、いろいろ出てくるねえ。ていうか一番出てくるねえ」。グラフィックの問題は見える（真っ白になれば一目）し直す場所も閉じてる＝出た瞬間に全部見えてる。ロジックの問題はシステムとシステムの隙間に隠れていて、隣をつついて初めて顔を出す＝自己申告しない。このセッションで出た「攻補(列)が6ファイルに配線されてた」「sim が思ってたのと違うものを測ってた（構造 vs 分布）」「仕様書とコードの乖離（initial_attack_mult）」は全部"今日作った問題"でなく"前から埋まっていた問題が掘られて顔を出した"もの。むしろプロト1で出し切れたのは良いこと（生成系はこの隠れ方が100倍になる予告編）。「見えないものほど膨らむ」という、ロジック作業の体感そのもの。

## initial_attack_mult → initial_attack_bonus へ変更。全7シナリオ再確認 PASS

### 変更内容

`initial_attack_mult`（乗算 float）を `initial_attack_bonus`（加算 int）に変更した。

**変更理由：** 乗算は溜め攻撃（×2）に重なると `16×2×1.5=48` など急激に跳ね上がり、計算可読性が低い。加算なら「溜め後の大ダメに＋N」として直感的に把握できる。

**変更ファイル：**
- `scripts/data/enemy_data.gd`：フィールド名・型変更（float→int, default 1.0→0）
- `scripts/battle/battle_unit.gd`：初期化条件 `initial_attack_mult > 1.0` → `initial_attack_bonus > 0`
- `scripts/battle/battle_manager.gd`：回転時リセット条件・ダメージ計算を乗算→加算に変更（`await`/Signal含む→実機確認必須）
- `scripts/battle/enemy_generator.gd`：B1=0, B2=4, B3=5
- `tests/test_battle_sim.gd`：`_make_enemy` シグネチャ更新、敵値更新

### チューニング過程

**B1 initial_attack_bonus の決定**

ROTATEのたびに `first_attack_active` がリセットされるため、毎ターンROTATEするB1-RではATK+bouns が毎攻撃に乗る。bonus=3→B1-R 68%（NG）、bonus=1→78%（惜しい）、bonus=0→90%（✓）。B1は入門戦・ROTATE有利が設計意図なので0が正解。

**B3 KNIGHT防御の重要性**

B3フォーメーションでGLADIATOR（atk_bonus=12所持）がSUPPORT_TARGETに狙われる。溜め後のNORMAL=16×2=32にbonusが乗る。KNIGHTがcol=2で防御（def_bonus=12）→32+5-12=25ダメージ。GLADIATOR(28HP)が3HP残って生存。bonus=5が通るギリギリのライン。
